# AMD firmware source evidence, baseline 26.06

The packaged catalog is an inventory of upstream source targets. Its selected baseline is the [coreboot 26.06 release tag](https://github.com/coreboot/coreboot/releases/tag/26.06), peeled to commit [`5cbf8afc4c08949c9b4ee1cb9dc5439add8a937e`](https://github.com/coreboot/coreboot/tree/5cbf8afc4c08949c9b4ee1cb9dc5439add8a937e). The annotated tag object is `0c3c7f09b0da2bb2056bb796654356032848eadd`; it is not the source commit. The tree was checked on 2026-09-22. Source links below contain the commit, so later changes to a branch or a documentation site cannot silently change the cited code.

The inventory scanned `src/mainboard/*/*/Kconfig` for selected AMD SoC or AMD PI symbols and paired each matching file with its `Kconfig.name`. That yielded 20 mainboard directories and 48 selectable board symbols. It also records 12 SoC configuration paths, including variants within shared source directories. These are source-tree counts. They are not counts of retail products, buildable recipes, successful builds, or hardware tests. A board using a less direct Kconfig relationship could be outside this scan; historical boards removed before 26.06 are outside this baseline.

Three ASUS desktop board symbols and one Family 15h TN processor-family record come from a separate historical baseline: [coreboot 4.18](https://github.com/coreboot/coreboot/tree/f4c97ea131944c7be940b35361407e4b63a14faf), commit `f4c97ea131944c7be940b35361407e4b63a14faf`. Its annotated tag object is `db77274669a732524766193a8f5db7f29e14065d`. These entries are marked `historical_release_only`. They are absent from the selected 26.06 mainboard tree and have no project recipes.

The machine-readable records are [targets.json](../../src/amd_fw/data/targets.json) and [evidence.json](../../src/amd_fw/data/evidence.json). Each source record has a precise location, retrieval date, revision where available, positive claim, and explicit limit. A source-tree entry gets `upstream-target-identified`; it does not get a project recipe or build status until those actions are independently recorded.

## Catalog state and dependency policy

`kind: soc` means a silicon/platform implementation path exists in the selected tree. `kind: board` means an exact Kconfig board symbol exists. Neither alone means the project has a firmware recipe. Only a board with a reviewed recipe may gain a `recipe_id`; a successful build is recorded separately from emulator and hardware results. `kind: research_case` has no build recipe. The APU2 and StarBook Cezanne entries currently have implemented, locally build-verified recipes. Every other board entry remains a source target or a historical target without a project recipe.

For binary components, the records name a known requirement only where the cited board source or documentation identifies it. `binary_only_licensing_unresolved` means source and redistribution rights were not established by the cited material; it does not say the bits are unlawful to use or absent from a public server. Other board records retain `input_audit: not_completed`. Do not infer an empty dependency list from that state. A host firmware source license does not license AMD security-processor, FSP, AGESA, EC, graphics, or microcode binaries.

The HP research entry uses public vendor documents for product options and
processor identity. A private archive was also reviewed offline. Its technical
observations and collection findings remain only in the excluded private
report because no owner-reviewed allowlist export has been approved for Git.
The public vendor sources do not authenticate the survey or identify a
particular unit. No physical hardware access, flash read, flash write, boot
test, or physical experimentation on the surveyed machine is part of this
project.

## Remaining research questions

- Audit the exact 26.06 input paths and licenses for any implemented board recipe. Record file hashes and source revisions without committing restricted binaries.
- Confirm whether each board's Kconfig symbol has revision constraints in board documentation or vendor records. Unknown is an explicit state.
- Record build outputs and repeat-build results as validation events rather than changing the meaning of `upstream-target-identified`.
- Extend the scan with reviewed mappings for older release branches and indirect AMD board Kconfig structures. Mark removed targets as historical with their own pinned revision and maintenance context.
- Keep the private survey interpretation separate from the public HP product option list. A possible Barcelo R processor relationship is not a Cezanne mainboard port.
